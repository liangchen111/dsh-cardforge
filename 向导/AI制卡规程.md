# ElecKoi 制卡规程

> 这份文件是给**能读写文件、能跑命令的 AI** 读的。
> 你的任务：把用户「想要一张卡」变成一张**能导入 ElecKoi、体检 0 错**的卡。
> 工具是 `forge.py`。**唯一真相是 `source/<名>.spec.yaml`，`成品/<名>.card.json` 是派生物。**

读完这份文件你应该能做到：自己问清需求 → 建工程 → 写内容 → 体检 → 出成品 → 交付，
全程不需要用户懂任何字段名。**手上已经有一张现成的卡也一样**（收进来再改，见 §二）。

## 一、开工流程（照这个顺序做）

```
# 0. 先问，别编
#    缺信息就问，一次最多问两三个问题。问完立刻给草稿让用户挑，
#    不要连问十轮，也不要用「神秘」「强大」这类空词占位。
#    要问清楚的：这张卡想让人体验什么 / 什么调子 / 世界 / 故事 / 玩家是谁 / 有哪些角色

#    这份规程随时可以再取出来看，不必等人贴给你：
#    `python forge.py guide` 出目录；`guide --节 三` / `--篇 预算` / `--对话 访谈` 取一段。
#    （装了「制卡工坊」插件就走 cardforge 工具：["guide","--篇","写法"]）
#    一段比全文省得多 —— 一万七千字一次塞进上下文既贵又冲淡重点。

# 1. 建工程 —— 先看清你手上有什么，再挑一条路开工。
#    `forge.py` 就是这个工具本身，装在哪儿问用户（或者你先试着把它跑起来）。
#    下面每条命令都在「你想让工程落地的目录」里跑，`forge.py` 用它的真实路径去调。
#
#    ★ **先看你手上有没有 `cardforge` 这个工具。**
#      有（ElecKoi 里装了「制卡工坊」插件就会有）→ **就用它**：把它当命令行用，
#      下面每条命令按词拆进 `args`，工作目录放 `cwd`。
#      它由**宿主进程直接执行，不受命令行沙箱限制** —— 所以**不要加 `--沙箱`**
#      （加了反而丢掉原子落盘）。
#      没有 → 用你自带的命令行工具（pwsh 之类）照下面跑，并看紧接着的这一段。
#
#    ★ 要是你正跑在**一层受限沙箱**里（读得到、写得进，但**删不掉文件、改不了名**，
#      报错是拒绝访问 / WinError 5）—— 比如在 ElecKoi 里直接用命令行工具就是这种环境 ——
#      那么**每条命令后面都加 `--沙箱`**（或者先 `FORGE_SANDBOX=1`）。
#      它让工具「只创建、只覆盖」，不碰删除与改名。
#      不加的话，`new` 与每一次改内容都会在落盘那一步被拒。
#      代价：丢掉原子落盘。**不在沙箱里就别加。**
#
#    ★ 然后挑一条：
#      **甲**、内容一次说得清（访谈得差不多了，或者手上就有一份定稿）
#           → 写一份卡稿，**一次落成**，一趟出成品：
#             python forge.py make 我的卡.yaml
#           稿子怎么写，两条路自己挑（都能直接打印出来看，不用去翻文件）：
#             `python forge.py make --模板` —— 一份骨架：只回答「有哪些键、怎么缩进」。
#             `python forge.py make --示例` —— 一**张真能开的卡**（长夜便利店）：
#                连「话该写多细、哪句放常驻、哪句放关键词」一起示范。
#                **照它改，比对着空文件想快得多 —— 优先走这条。**
#           （同一份示例也落在 `向导/示例卡稿.yaml`，与规程放在一起。）
#           条目按**标题**认人（卡里已有同名的改它、没有才新建），分组与变量对象
#           缺了自动补 —— 不必先摸清骨架、也不必背命令的先后。稿子有毛病时它
#           **一个字都不会往目标位置写**（先把稿子改对再落）。
#           改完稿子想重落：加 `--覆盖`（只认同一张卡，别的东西不碰）。
#
#      **乙**、边聊边做（更常见）→ 按下面一路做下去：
python forge.py new 我的卡 --模块 骰子,备份        # 模块可省
#    → 工程落在 <当前目录>/我的卡/
#    → 规格文件（本文下面写作 <spec>）就是 我的卡/source/我的卡.spec.yaml
#      命令里一律写这个完整路径；卡名带中文也没关系
#    想先看有哪些现成机制可接：python forge.py mods

# 2. 先看骨架里现成有什么，用不上的删掉
python forge.py entry <spec> --列                    # 条目：分组 / 触发 / 策略 / 字数
python forge.py entry <spec> --删 "规则 · 判定"       # 删错了能捞回来，见本节末

# 3. 逐条换成你的内容 —— 先读、再改；改已有的用 --改，别删了重建
python forge.py entry <spec> --看 "核心 · 世界总纲"   # 先读它现在写了什么、怎么触发
python forge.py entry <spec> --改 "核心 · 世界总纲" --正文 "……"
python forge.py entry <spec> --改 "名册 · 常用名字" --标题 "名册 · 常客" \
        --正文 "……" --提示 "玩家问起某个人名时读这条"
python forge.py group <spec> --新 角色                # 要用的分组先建出来
python forge.py entry <spec> --新 "角色 · 阿岩" --模板 必读 --分组 角色 \
        --提示 "玩家和店员对话、或问起他时读这条" --正文 "……"
python forge.py entry <spec> --新 "世界 · 长夜便利店" --模板 关键词 --分组 世界 \
        --关键词 便利店,夜班,冷柜 --提示 "玩家问起这家店、夜班规矩时读这条" --正文 "……"
#    ↑ 加新条目时别忘 --分组：不写就全落在「未分组」，做出来的设定库是一盘散的
python forge.py var   <spec> --新 玩家.信任 --类型 number --初值 0 --说明 "……"
python forge.py regex <spec> --列

#    要写的正文一长（几百字、还分好几段），**别往命令行里塞** ——
#    换行和引号在 shell 里是另一门手艺，各平台还不一样。写成文件再 @ 进来：
python forge.py entry <spec> --改 "核心 · 世界总纲" --正文@世界总纲.txt
#    （`--正文 @世界总纲.txt` 空格隔开也行；凡是要写一段话的地方都认 @文件）

# 4. 开场白 —— 它不在 spec 里，用 opener 改（见下一节）
python forge.py opener <工程> --正文@开场白.txt

# 5. 每改一轮就体检
python forge.py check <spec>          # 单文件：详表 + 错误 + 警告 + 提示，全看得到
python forge.py check <工程目录>       # 整目录：批量模式，只报错误数，警告与提示折进去

# 6. 出成品（交付给 ElecKoi 的就是这个）
python forge.py build <spec> 成品/我的卡.card.json

# 6b. 两张「拿去导入」的皮（都只是加法，不动卡里任何内容）
python forge.py png    成品/我的卡.card.json     # → 成品/我的卡.card.png：带图的卡，手机端就认这条
python forge.py preset 成品/我的卡.card.json --png  # → 成品/我的卡.preset.{json,png}：创作预设（导入时分类选「创作预设」）

# 7. 交付（顺手出人读手册与给 AI 的索引；不给 -o 就落在 <工程>/文档/ 下）
python forge.py manual <spec>
python forge.py index  <spec>
```

七条要记住的：

- **命令的用法就在它自己身上。** 忘了参数别猜：`python forge.py entry --help`
  会打出这条命令的全部参数（`python forge.py --help` 是总表）。
- **先读再改。** `python forge.py entry <spec> --看 "<id 或 标题>"` 打一条条目的全貌 ——
  正文全文（原样，带换行）、关键词、读取提示、触发方式、插入位置… 读它一个字都不落盘。
  改之前先看一眼它现在写的是什么、靠什么触发；不先读就改，等于闭着眼动刀。
- **写命令要一条一条来，别并发。** 同一份 spec 上同时跑两条改内容的命令，两条会各自读到
  同一份旧内容，**后落盘的那份赢**，前一条静默消失。工具现在会拒掉第二条（告诉你
  「这个 spec 在你读它之后被改过了」），但别去试它 —— 串着跑就不会遇上。
- **`--新` 加出来的条目默认落在「未分组」。** 想归组再挪一下：
  `python forge.py entry <spec> --挪 "条目标题" --到 世界`（`group --列` 看有哪些分组）。
- **一次动多条：`--复制` / `--挪` / `--删` / `--启用` / `--停用` 后面都能跟一串。**
  `python forge.py entry <spec> --挪 甲一 甲二 甲三 --到 世界`、
  `entry <spec> --删 旧一 旧二`。一次落盘、**一条**回收记录（`trash --还原 N` 一次全捞回来）。
  有认不出的名字就**整批停下**、一条不动 —— 「挪了 10 条其中进了 6 条」是最难收拾的状态。
  单条的老写法一个字不用改。
- **`--复制` 是「照着这条再来一条」。** 副本顺着原件排在最前面那条的后面、默认叫「原名（副本）」、
  正文原样、id 全新（所以卡里引用旧 id 的地方不受影响）。`--到 分组` 能让副本直接落进那个组，
  不给就跟着原件待在同一个组。复制跟 `--新` 一样**不写回收记录** —— 不想要了 `--删` 掉它。
  **开场白条目不许复制**，一张卡只有一条开场白（要多一个开场方案用 `opener`）。
- **`--改` 后面跟一串，就是批量改字段。**
  `python forge.py entry <spec> --改 甲一 甲二 --正文 "…" --提示 "…"`：
  这批条目同时改成同一组字段，一次落盘、**一条**回收记录。
  值域照旧当场拦，而且按**批次**判 —— 只要有一条会被静默降级，**整批一个字都不落盘**。
  它省的是「同一段话抄十遍」，不是「要不要想清楚」：一次改十条之前先想清楚这批是不是真该一样。
  注意**开场白的正文不能这么改**（真源在界面配置里、末尾还挂着零宽标记），要改走 `opener`；
  勾里混了开场白时它会直接拦下并告诉你。
- **长正文用 `--正文@文件`。** 值写成 `@文件名` 就从那个文件读内容 ——
  任何 shell、任何长度、带不带换行与引号都一样，末尾一个换行按习惯忽略。
  文件名写错会**当场报错**（绝不会把那串 `@名字` 当正文写进卡里）。
  凡是「要写一段话」的参数（正文 / 标题 / 说明 / 正则模式与替换）都认这个写法。
- **改已有的条目一律用 `--改`。** 它只动内容与偏好，id / 顺序号 / 分组位置一概不动 ——
  删了重建会换 id，卡里引用旧 id 的地方就断了。能改的字段：标题 / 正文 / 关键词 /
  读取提示 / 触发方式 / 读取策略 / 插入位置 / 插入角色 / 内容模式 / 图标 / 启用。
- **值域字段写错会被当场拦下，而且一个字不落盘。** 比如把读取策略写成
  `variable_condition`，它会直接告诉你「这会被静默降级为 normal」。
  看全部合法值：`python forge.py domains`（它末尾还单列了**插入位置**该填什么：
  留空＝不占提示词位，`instructions`＝进系统提示词区）。
- **看卡里现在有什么**：`entry --列`（带分组 / 触发 / 策略 / 字数 / **启用**）/
  `var --列` / `regex --列` / `group --列`。
  `entry --列` 最后一列写「禁用」的，是**卡里留着但不生效**的条目（从酒馆收来的常见）——
  想让它生效：`python forge.py entry <spec> --改 "标题" --启用`。
  **改卡名用 `name`**：卡名写在 spec 与界面配置两处，`python forge.py name <工程> --看`
  看它们一致不一致，`--改 <新名>` 一次改两处。（卡名对不上，导进 ElecKoi 显示的
  会跟工程目录不一致，`check` 也会报 `PROJ-NAME-DRIFT`。）
  **改变量名 / 变量对象名用 `var --改名`**：名字不是一个孤立字符串 —— 它同时是
  面板上那一行、初值里那一格的**键**、Zod 里那个**字段名**。只改一处，另两处就悄悄悬空
  （运行时静默丢值）。`python forge.py var <spec> --改名 "面板.声望" --成 "名望"`，
  对象同理：`--改名对象 面板 --成 状态板`（子对象整棵跟着走）。
  **id 不动** —— 卡里按 id 引用的地方不会断（删了重建才会断，别那样干）。
  正文里写着旧名字的地方工具**只报不改**：它分不清那是变量名还是恰好同字的常用词。
  **删错了不怕**：删除和字段改动都进 `<工程>/.workbuddy/回收站/`，
  `python forge.py trash <工程 或 spec>` 看有什么，`--还原 N` 捞回来。

## 二、手上已经有一张卡（不是从零开始）

用户给你一张卡 —— 自己在别处做的、别人发的、或从酒馆迁过来的。
先弄清它是哪一种，再决定走哪条路：

```
python forge.py analyze <卡文件…>                  # 只看：它是什么卡、几条条目、多少字、变量正则几个
python forge.py import  <包.zip 或 卡.json> [--到 目录]   # 收成本地一张能接着改的工程
python forge.py new <卡名> --从 <卡.json / 包.zip / spec.yaml / 工程目录>   # 开一张带界面的新卡，内容层用它
python forge.py to-eleckoi <酒馆卡.json> <出.yaml>          # 酒馆卡 -> ElecKoi 的 spec 草稿
```

- **先 `analyze`，它只读不落盘。** 打出来的第一件事是「识别为」——ElecKoi 角色卡、还是酒馆卡
  （V1/V2）；接着是名字、条目数与分组数、变量与正则个数、正文合计多少字。
  **看一眼再动手，别猜**；用户说「我的卡」时尤其要先确认他给的是哪一种。
- **第一个决定是「要不要卡内界面」**：

  | 想要什么 | 用哪条 | 拿到什么 |
  |---|---|---|
  | 只想改内容 / 改开场白 | `import` | 一个内容层工程（`source/` 一层） |
  | 想要卡里的面板 / 建卡器 / 悬浮球 | `new <卡名> --从 <卡>` | **完整工程**：界面层照抄骨架，内容层用卡里的 |
  | 只想把酒馆卡读懂 | `to-eleckoi` | 一份 spec 草稿（见下面那条） |

- **`new --从` 就是「把条目搬过去」这条路**（以前没有命令，只能人肉重建十一条目加十个变量）。
  界面层照抄骨架（面板 / 建卡器 / 悬浮球都在，通用代码，不含世界观），内容层整体换成卡里的。
  **条目 id 保持原样** —— 卡里变量、正则、条目按 id 互相引用，改名就断链。
  **卡名以你给的新名为准**（`--从` 只借内容）：spec 和界面配置都会是新名，
  不会留着来源卡那个旧名。
- **来源里「已禁用」的条目照原样留着**（卡里留着，但不生效），`new` 会数给你听。
  想让它生效：`python forge.py entry <spec> --改 "标题" --启用`；
  想确认还有哪些是禁用的：`entry <spec> --列` 看最后一列。
- **单张 `.card.json` 里没有界面层。** `hud/` 本来就不在卡里，所以 `import` 下来只有 `source/`，
  不算丢东西；**没有界面层不影响改内容，也不影响改开场白**（`opener` 两种工程都认，见 §三）。
  **别以为收漏了文件。**
- **多套开场白是有损的。** 酒馆卡常带好几套开场（默认 + 备选）。走 `new --从` 时骨架的建卡器
  只有一格正文，写回会把各方案统一成默认那套（工具会当场告诉你丢了什么）。想保住多套：
  用 `import` 收成内容档，各方案各自留着。
- **酒馆卡转过来的是草稿，不是成品。** `to-eleckoi` 会在末尾打三条提醒，照着处理：
  插入位置要人工确认（酒馆有 8 个位置，只做了粗略映射）；概率触发 / 包含组 / 向量匹配 /
  递归扫描在 ElecKoi 侧没有等价字段、没转；变量要在 ElecKoi 里重新定义。
  转完先 `check`，再按 §一 第 3 步往下改。
- 收进来的工程跟 `new` 建的一样，后面照 §一 第 2 步往下走。
- **别往只读参考目录里 import** —— 有些目录是禁区，命令会自己拒绝，不让写。

收完先跑一遍 `check`，看看接手的底子什么样，再动内容。

## 三、开场白（别去改任何文件，用 opener）

开场白是权重最高的字段（见「写法」），但它**不是普通条目** —— 别拿 `entry --改` 动它的正文
（工具会直接拦住：那条正文末尾挂着三个零宽标记，`--改` 会把标记一起抹掉，还不报）。

它的**真源在哪，看工程有没有界面层**：

| 手上的工程 | 真源 | 改起来的后果 |
|---|---|---|
| 有 `hud/hud.conf.json`（`new` 建的） | conf 里的 `"开场白" → "正文"`；spec 里那条 `AI角色开场白` 是**派生物** | 直接改 spec 那条＝**改了白改**，下次写回被一字不留地冲掉 |
| 只有 `source/`（`import` 进来的单张卡） | **spec 里那条本身就是真源** | 直接改它就是对的，没有「改了白改」这回事 |

**一条命令，两种都认** —— 末尾那三个零宽标记也由它负责：

```
python forge.py opener <工程 或 spec> --看               # 先看：正文、标记几个、真源在哪
python forge.py opener <工程 或 spec> --正文@开场白.txt   # 换正文（标记自动补齐）
python forge.py opener <工程 或 spec> --补齐             # 标记少了，补成正好 3 个
```

`--正文` 默认改完顺手写回（有界面层时；内容档没得写回，`--看` 会说明）。

**末尾那三个零宽空格（U+200B）是干什么的。** 「建卡界面」那条正则
（`pattern: /\u200B{3}/`）就是靠它触发的 —— **少一个，导入 ElecKoi 后建卡界面
根本不会出现，而 check 原先也不报。** 自己数、自己补都是踩雷的路；`opener`
负责末尾**不多不少正好三个**（你给了几个都不算数）。所以：

- 换正文只管写内容，标记不用管（多写了也会被规整）；
- 正文里**不能有尖括号** `<` `>` —— 那会把标记变回可见字符，从会话预览里露出来，
  `opener` 会当场拦住；
- 手改过 conf、把标记弄丢了：`--看` 会告诉你「末尾 1 个 ✗ 该是 3 个」，`--补齐` 补回来；
- 不想要卡内建卡界面、也不想开场白带尾巴字符 → 把 conf 里「开场白」整块删掉，
  之后开场白交给宿主填（`opener` 会说「这个工程没有开场白」）；
- 改错了不怕：旧版在回收站里（`python forge.py trash <工程> --还原 1`）；
- 绕过 `opener` 手改 conf 也不是没人管 —— `python forge.py check <工程>` 兜底：
  标记少了报 `HUD-OPENER-MARK`，spec 里那条与 conf 对不上报 `HUD-OPENER-DRIFT`。
  **这两条只在「有界面层」的工程上守** —— 没有界面层就没有 conf 可比、也没有那条正则；
  内容档改完就是最终状态，不用写回，也别指望 check 来兜。

## 四、把卡拆开改

| 文件 | 是什么 | 能不能手改 |
|---|---|---|
| `source/<名>.spec.yaml` | **唯一真相**，卡的全部内容 | 能改内容，别改结构；条目优先用 `--改`；**卡名用 `forge.py name` 改**（手改 spec 会跟界面配置脱节） |
| `成品/<名>.card.json` | 派生物，交付给 ElecKoi 的就是它 | **不能改**，下次构建就没了 |
| `成品/<名>.card.png` | 带图的卡（`png` 出）——**手机端导入只认这条**，JSON 在手机上导不进 | **不能改**，重出覆盖 |
| `成品/<名>.preset.json` / `.preset.png` | 创作预设（`preset` 出）：**卡怎么做出来的经验**，导入时分类必须选「创作预设」 | **不能改**，重出覆盖 |
| `hud/` | 界面层（面板 / 悬浮球 / 建卡器） | 能改，改完必须 `hud --写回` |
| `hud/hud.conf.json` | **开场白的源头**、模块名单、id 前缀 | 能改，改完 `hud --写回` |
| `模块账本.json` | 接过哪些机制、并进来了什么 | **别手改**，撤模块全靠它 |

## 五、内容怎么写（方法论九篇）

### 机制 · 一张卡由什么构成

【一张 ElecKoi 卡由什么构成】

一张卡 = 角色壳 + 设定库 +（可选）变量 +（可选）正则 +（可选）界面 +（可选）图片。

- 角色壳：只有名字和挂载关系。**先建壳，再往里放东西**；名字后改的成本几乎为零。
- 设定库：卡的主体，装所有内容。两条固定条目动不得：`AI角色开场白`（开卡第一屏，可有多个方案）、`角色扮演任务计划`。
- 变量：要记住「会变的状态」时才加（好感度、时间、金钱、进度）。动手前三件事答全：**哪些字段、初值多少、什么条件下更新**。答不全就先别加。
- 正则：只管显示格式（清理、替换、给正文加样式），不承担内容。
- 界面：卡可以自带一层页面内界面（面板 / 悬浮球 / 建卡器）。不是必需品，内容立住之前不要碰。
- 图片：三个彼此独立的槽位——圆形头像、方形头像、3:4 立绘。

【一条内容该放哪一层】

| 这条东西的性质 | 放哪 |
|---|---|
| 每轮都必须生效、不可违背 | 常驻条目 |
| 细则、资料、专有名词 | Agent 读取（靠标题 + 选择提示被找到） |
| 体积不大、每轮都要、但不算铁律 | 缓存设定 |
| 会变的数字或状态 | 变量，不要写成文字塞在条目里 |

写任何一条之前先问自己：**这条是「规则」还是「资料」？**
规则要短、要硬、要少；资料要多、要可查、要能被关键词命中。
两者混在一条里，最后一定两头不讨好。

### 机制 · 条目触发方式怎么选

【条目触发方式怎么选】

ElecKoi 的条目只有两种触发方式（`trigger_mode`）：

- `always` 提示词常驻：每轮自动注入。适合核心身份、不可违背的准则。要指定**插入位置**与**插入角色**；位置越靠前，约束力越强。
- `agent_tool` 由 AI 读取：条目先进 AI 可见的目录（**只给标题 + 选择提示**），再由读取策略决定何时真正读出。

`agent_tool` 之下有三种读取策略（`agent_read_strategy`）：

- `required` 必读：每轮强制读出。
- `normal` 选读：AI 看标题和选择提示自行判断。
- `keyword` 关键词：扫描最近若干条消息，命中关键词才提升为本轮必读。

【怎么选】

- 少而硬 → `always` 常驻。
- 多而杂、按需查 → `agent_tool` + `normal`，**每条都要写一句「什么时候读我」**。
- 靠专有名词就能命中 → `agent_tool` + `keyword`。关键词写**玩家真会说出口的词**，不要写你内部的分类名（写「灰港」「码头」有用，写「地理设定条目」没用）。
- 拿不准 → 先 `normal`，观察它是不是真被读出来，再决定要不要升级成必读或常驻。

选择提示（`agent_selection_hint`）是选读条目的生死线：没写它，AI 只看得见标题，多半不会来读。

### 预算 · 每句话都在跟聊天记录抢位置

【预算 · 每句话都在跟聊天记录抢位置】

每轮都在注入的内容（常驻条目、核心身份）= **固定税**；被触发才进来的条目 = **条件支出**。
两者都在跟聊天记录抢同一块位置。常驻写得越胖，AI 忘掉最近对话就越快 ——
玩家抱怨「它忘了我们刚才说的」，九成不是模型笨，是卡太胖。

一个可用的参照（按中文字数）：

| 部分 | 目标区间 |
|---|---|
| 核心身份（常驻） | 150–400 字 |
| 铁律与限制 | 200–400 字 |
| 开场白 | 200–500 字 |
| 示例对话 | 2–3 轮，每轮 60–150 字 |
| 条目（单条） | 300–800 字 |

超过 1200 字的条目，先考虑拆成两条；整张卡的常驻总量超过 1500 字，先删再说。
**删比加快**：删掉一句没人用的话，收益是每一轮都省。

省字数的三个具体做法：
1. 同一件事只说一次（见「红线」第 7 条）。
2. 形容词换成可观察的行为（见「写法」）。
3. 把世界细节从常驻挪进条目 —— 不提它的时候，它一分不花。

### 世界 · 世界观设计清单

【世界观设计清单】

一次只定一层，定完再往下。

1. **调子**：这个世界给人的第一感受。现实向／都市异能／东方幻想／西幻／科幻／废土，或一句具体画面（比如「永远阴天的港城」）。调子决定后面所有取舍，**先定它**。
2. **舞台与时代**：发生在哪、什么技术水平、日常生活长什么样。写三条具体细节，比写一段形容词有用。
3. **规则边界**：有没有超自然。力量从哪来、代价是什么、谁掌握它。规则不清的世界，剧情随时会崩。
4. **知情范围**：普通人知不知道异常存在。这决定秘密、谎言和紧张感的来源。
5. **当前状态**：故事开始时，世界正处于什么局面（战争将起、王朝更替、秩序刚崩）。有「正在发生的事」，角色才有事可做。
6. **日常质感**：吃什么、怎么称呼、钱怎么花、忌讳什么。这是让世界「活」起来的地方，也是描写最容易写飘的地方，值得单独写一条。

【怎么落成条目】

- 世界总览 1 条：要短，常驻或必读。
- 规则、势力、地点、历史：Agent 读取 + 关键词，**专有名词做关键词**。

世界条目不要写成小说，写成**可查的事实卡** —— AI 要的是能直接引用的事实，不是氛围散文。

### 故事 · 主线、冲突与节奏

【故事线设计】

世界立住之后，回答一个问题：**这个世界正在发生什么，而玩家被卷进哪里。**

1. **核心冲突**：谁想要什么、谁挡着、为什么不能简单解决。冲突必须有「不能一走了之」的理由。
2. **主线与支线**：主线 1 条、支线 2–3 条。支线用来展示世界的其它面，不要都指向同一个结局。
3. **玩家的席位**：他在故事里是谁——当事人、局外人、还是被卷进来的人。这个位置决定开场怎么写、角色怎么对待他。
4. **紧张感从哪来**：资源稀缺、时间压力、身份不能暴露、关系会破裂。至少选一个，否则剧情会退化成没有代价的聊天。
5. **推进节奏**：分阶段（平静 → 起疑 → 摊牌 → 付出代价 → 新局），每阶段写明「会发生什么、满足什么条件进入下一阶段」。这是条目与变量的依据。
6. **开场时机**：从「事情已经不对、但还没爆」的那一刻开始最抓人。不要从世界诞生讲起。

【一句话检验】

如果你不能用一句话说清「**谁、想要什么、被什么挡着**」，说明主线还没立住，先别写角色。

### 角色 · 角色条目拆分法

【把角色落成条目】

世界和故事定好之后，才逐个细化角色。一次只做一个。

一、先定「位置」，再定「人」
角色在世界与故事里承担什么功能——对手、引路人、旧识、旁观者、某个势力的代表。
位置决定戏份和关系。先挑位置，再往里面填血肉：**位置可以有几个备选，人只能有一个。**

二、每个角色拆成这几条

- **身份与经历**：他是谁、怎么变成现在这样。用「因为……所以……」写因果，别只堆事件。
- **性格与说话腔调**：写腔调必须给例句（见「写法」那一条）。
- **关系**：对玩家、对其他角色的态度，以及这份态度的来由。
- **外在形象**：外貌、穿着、标志性动作。这一层优先级最低，AI 能自己补，别花太多字。
- **秘密与底线**：什么绝对不会做、什么绝对不能碰。这条决定角色会不会崩。

三、触发方式怎么配

- 核心身份与腔调 → 常驻或必读，每轮都在。
- 经历、关系细节、秘密 → Agent 读取 + 选读，聊到才拉出来。
- 需要随剧情解锁的一面 → 关键词，用剧情里的转折词做触发。

四、一致性检查

写完对一遍：这个角色此刻该不该知道这件事？他的说话方式在多条条目里是否一致？
有没有「作者需要他做的事」和「他会做的事」冲突——**有冲突就改设定，不要靠剧情硬掰。**

### 写法 · 怎么把角色写活

【写法 · 怎么把角色写活】

这一条是「怎么落笔」，比结构更影响最终手感。

一、**写行为，不写形容词**
「她说话很温柔」没用。改成：「她每句话结尾习惯加一个『~』，从不大声说话，被夸的时候会先低头。」
形容词是结论，行为是证据 —— AI 只能照着证据演。

二、**正向表述，别写禁止**
模型会咬住禁止句里的词，然后照做。「不要提自己是 AI」不如写「她坚持用角色的身份说话」。
确实要设死线时，把它放进「秘密与底线」，用陈述句写清楚。

三、**散文，不要伪代码**
`[Character("灰港")|Personality("冷淡"+"防备")]` 这种格式浪费字符，现代模型读段落读得更好。
列表可以用，符号不要用。

四、**开场白是权重最高的字段**
它一次性定了地点、语气、句子长度、动作与对白的比例，模型会整段照抄。
- 从角色的视角写，至少有一句他的原话。
- **别用问句结尾** —— 那会把模型训练成「问一句答一句」的循环。
- 开场就进入「事情已经不对、但还没爆」的那一刻。

五、**示例对话是最强的风格锚**
2–3 轮带标签的短例子，胜过一段关于腔调的形容。格式：

```
{{user}}: 你以前不是干这个的吧？
{{char}}: 她把抹布搭回肩上，没抬头。「谁以前都是干别的。现在我是擦桌子的那个。」
```

**不要**把玩家的动作写进 `{{char}}:` 那一行 —— 模型会学着你抢玩家的戏。

六、写完自己念一遍
念出来别扭的地方，AI 读起来也别扭。

### 变量 · 什么时候需要变量

【什么时候需要变量】

只在「需要记住**会变**的状态」时加变量。加之前三件事答全：

1. **哪些字段**：好感度、时间、金钱、伤势、任务进度、已解锁信息。
2. **初值是什么**。
3. **什么条件下更新**：由谁更新、什么时候更新、更新多少。

三件事答不全就先别加。**加了没人更新的变量，等于给 AI 埋了一个永远不动的假状态** ——
比没有更坏，因为它看起来像真的。

【变量在卡里其实写了三处】

一条变量必须同时写进三个地方：变量对象（面板上那份）、初始状态（开局那份）、
Zod 校验码（决定写进去的值留不留得住）。三处**少任何一处都不报错**，
只是运行时静默丢掉写进去的值 —— 这是 ElecKoi 制卡最容易踩、也最难查的坑。
手改极易漏；用工具加变量（`forge.py var`），三处一次写齐。

**改名同理**：变量名本身就是初值那一格的键、也是 Zod 里的字段名。所以改名字
不能手改，用 `forge.py var <spec> --改名 "面板.声望" --成 "名望"` —— 它把三处
一次挪过去，id 不动（卡里按 id 引用的地方不会断）。**别删了重建**：那换的是 id，
引用全断。对象改名用 `--改名对象`。

**换对象也一样**：把一个变量从「面板」挪到「背包」下，名字不变，但**它要在另一棵
子树下重新出现** —— 手改会把初值那格漏在新对象的树外（值读不到），或把 Zod 那个
字段落在旧对象下（值写进去被静默丢掉）。用：
`python forge.py var <spec> --换对象 "面板.声望" --到 "背包"` —— 挂靠 / 初值那格 /
Zod 那个字段一起搬，顺带排到新对象末尾，id 不动。挪错了 `trash --还原` 能整个撤回来。

**一次删几个变量**：`python forge.py var <spec> --删 "面板.声望" "面板.金币"` ——
一次落盘、**一条**回收记录（`trash --还原 N` 一次全捞回来）。每个变量都牵着三处
（画面板 / 初值那格 / Zod 那个字段），所以这里是「三处 × N」一起撤。
有认不出的名字就整批停下、**一个都不删**。

【写法】

- 类型：字符串 / 数字 / 布尔 / 数组 / 对象。
- 名字写给人看（面板上显示的就是它），别用英文缩写。
- 数组能装结构（背包、属性表），但先用简单类型跑通，再考虑结构化。
- **同一个状态只能有一个家**：写进变量的东西，不要再用文字在条目里复述一遍。

### 界面 · 卡内界面要不要做

【卡内界面要不要做】

ElecKoi 的卡可以自带一层页面内界面（面板、悬浮球、开局建卡器）。
它由注入宿主页面的 CSS + JS 组成，靠卡里的一条正则把脚本送进去。

按这个顺序判断：

- **内容还没立住 → 不做。** 界面是放大器，把空内容放大还是空。
- 玩家要反复查看一组数字（属性、背包、好感度）→ 一个只读面板就够。
- 开卡时想让玩家填档案（名字、性别、初始设定）→ 建卡器值钱。
- 只是想换配色 → 用皮肤（只覆盖颜色变量），不要动界面代码。

真要做，守三条纪律：

1. **只覆盖颜色槽**（`--hud-*`），不重写版式 —— 换皮肤时才不会打架。
2. **类名一律带前缀**，别用 `.card`、`.title` 这种通用名 —— 宿主页面里会互相污染。
3. **改完必须重新写回卡**（组装界面并写回），否则界面进不了卡，导入后什么都不会发生。

### 玩法 · 让玩家觉得「被记得」

【玩法 · 让玩家觉得「被记得」】

玩家留下来的理由只有三条，按重要性排：**被记得 · 有后果 · 有进展**。
花哨的界面排在这三条后面 —— 内容没立住时，界面只是把空洞放大。

四种便宜又有效的做法（都能只用「条目 + 变量」实现）：

- **对账簿**：凡是「已经欠下 / 已经收下 / 已经说出」的东西，另立一条账，每轮末尾更新。
  别指望模型记得第 7 轮的一句承诺 —— 它记不住，但账本记得住。
- **在场名录 + 下一步动作**：每轮收尾，给**在场且有名有姓**的每个人写一句「他接下来打算干什么」。
  **写不出下一步的那个人，本轮就该让他退场** —— 这是治「NPC 变布景」最便宜的一刀。
- **未收的线**：立一个「还没兑现的线」清单，每行写清「什么线 / 埋在第几轮 / 打算怎么收」。
  它同时救了两个毛病：AI 把伏笔忘掉，和 AI 每轮旧事重提。
- **知情矩阵**：谁**知道**什么、谁**不知道**什么，写成分开的两栏。
  只要这一栏在，AI 就不会让不该知道的人知道 —— 比事后解释便宜得多。

写这些时守一条：**账必须有人更新**。加了没人维护的账，比不加更坏，因为它看起来是真的。

### 玩法 · 世界要会动，也要能查账

【玩法 · 世界要会动，也要能查账】

**可复现的随机**：要随机就别用「随便一个数」。写成「骰子值」＋「种子」两个变量，
AI 每轮先报出骰子值与来源，再据此叙事。好处是同一颗骰子能重放、能对账、能复盘 ——
玩家不信的时候，你拿得出数字。**但别把骰子丢进面板**：面板是给玩家看的，不是给 AI 算的。

**世界快照与回滚点**：长线卡每过一段（一章 / 一个任务）留一份「世界当前状态」的快照条目。
玩家说「回到那次之前」时你有东西可回；你自己改坏了也有东西可退。
这和工具侧的回收站是两回事：**回收站管你改卡，快照管剧情**。

**门**：需要「开过的路」时，把条件写成一个变量 + 一条判定句（「什么满足 ⇒ 什么发生」），
不要写成一段可以绕过的散文。

**配方层（下一件事从哪来）**：新卡最容易死在「第 30 轮之后没事发生」。
规划 4–8 条生成器：新角色从哪来 / 新地点怎么长 / 委托怎么发 / 遭遇怎么捡 / 价格哪儿查。

**口径卡**：把「这个世界里没有的东西」写成一张短表（有没有魔法、有没有神、钱叫什么）。
它比长篇设定省钱，而且直接掐掉 AI 的胡思乱想。

**游玩中改设定**：玩家中途说「其实我还有个哥哥」—— 处理成**加法**（新增一条 + 记进账），
不要回头改写已经发生过的段落。

### 前端 · 小手机不是一条正则

【前端 · 小手机不是一条正则】

小手机 / 面板这类东西，**不是消息楼里的一块正则 HTML**，而是挂在宿主页面上的东西。
按这个分工写，才不会写成一坨：

- **入口层**：悬浮球 / 移动端抽屉 / 浮窗 —— **只负责发命令**（打开这个、打开那个），
  自己**绝不读变量**。别再造第四套入口。
- **内容层**：面板 / 状态栏 —— 读变量、分页、接交互。
- **挂载层**：谁挂在哪、挂几份。**每楼一份的要自己去重**；挂在宿主页面上的**是单例**。

四条通用纪律（换任何宿主都成立）：

1. **别假定当前窗口就是主窗口**：脚本常跑在 iframe 里。最多向上找几层父窗口，
   摸到宿主的 `document.body` 为止；**所有输入框操作都走那个宿主窗口**。
2. **挂新的一份之前，先卸掉旧的**（用固定的键标记自己那份），否则监听会一层层叠上去。
3. **界面用 `data-*` 属性当协议**（样式改版不会打断逻辑），根上开 `container-type`，
   窄屏自动单列 —— 手机端是主战场，别只照桌面做。
4. **大段 HTML 绝不塞进开场白**：它不但撑爆首轮预算，还会让界面在错误的时机出现。

要「把 AI 写的选项变成按钮」时：正则只铺一个空容器，桥去找**最新一楼**的容器填按钮，
点击默认**填进输入框**（可多选再改），玩家勾了「直发」才真的发送。
**桥不写变量**，也别在面板里再做一套平行的选项解析。

### 前端 · 换宿主最容易死在哪

【前端 · 换宿主最容易死在哪】

这一族坑的共同点是：**不报错，只是什么都不发生**。记四条：

1. **壳与真身不在同一个窗口时，宿主的东西不会自动出现在你那边。**
   桥没补上，读变量会**静默返回空**，界面上全是 `--`。
   ⇒ **界面上出现成片的占位符，第一反应不是样式问题，是桥没通。**
2. ★ **仿真壳永远绿、真机红**：自己搭的仿真环境往往少了「壳 → 中间层 → 真身」那几跳，
   于是仿真里一切正常。⇒ **界面这一类改动，必须在真机上再走一遍**，
   仿真通过只能说明语法没错。
3. **面板画得出 ≠ 桥在**（同一条的另一种说法）：先确认最基础的一次变量读取真的通了，
   再去调版式。顺序反了会白调一天。
4. **换宿主时，哪些能搬、哪些不能，要分开标**：
   「找宿主窗口」「单例 vs 去重」「先卸再挂」「`data-*` 当协议」这些搬到哪都成立；
   而具体的变量读取接口、宿主菜单挂载点、聊天切换事件，**换个宿主就必须重写**。
   ⇒ 动手前先把这条对错表列出来，别照抄。

交付前对玩家只说人话：「手机上打开看一眼，面板里的数字是不是真的动」——
比让他读一百行调试日志有用。

## 六、验收标准（不满足就不要交付）

1. `python forge.py check <工程目录>` —— **0 错**。有错就别交，先改。
2. 卡打得出来：`python forge.py build <spec> 成品/<名>.card.json` 成功，
   且 `成品/*.card.json` 是**最新**的（改了 spec 没重出成品 = 用户导进去的还是老内容）。
3. 解包往返一致，具体是：
   `python forge.py unpack 成品/我的卡.card.json -o 回.yaml` →
   `python forge.py build 回.yaml 回.json` →
   `python forge.py diff 成品/我的卡.card.json 回.json` 报「语义完全一致」。
4. 接了界面的卡：`hud --写回` 跑过，且 `check` 不再报界面守则的问题
   （含开场白那两条 `HUD-OPENER-MARK` / `HUD-OPENER-DRIFT`）。
   ★ **还必须在真机上打开看一次**：自己搭的仿真壳常常少了「壳 → 中间层 → 真身」那几跳，
   结果**仿真全绿、真机一片 `--`** —— 仿真通过只能说明语法没错
   （见 §五「前端 · 换宿主最容易死在哪」）。
5. 交付时同时给：**成品卡**（导入用）+ **手册**（人读）+ **索引**（AI 读）。
   用户要在**手机上**导入，就得给 `png` 出的 `成品/<名>.card.png`（JSON 在手机上导不进）；
   想让「这张卡是怎么做出来的」也留一份给 AI，再给 `preset` 出的预设。
6. 用户如果要的是「一张卡」，不要说「你可以自己填一下 X」——填完再交。
7. 分清**成品卡**和**工程分发包**（两个都在，别混）：
   - `成品/<名>.card.json` —— 交付物，**导入 ElecKoi 用的就是它**（`build` 出）。
   - `<名>-分发包.zip` —— 整份工程（连界面层源码一起），发给**要接着改这张卡**的人
     （`bundle` 出；它会顺手重组界面、重出成品与手册）。用户说「给我卡」就给前者。

## 七、交付怎么说

给用户的话里只说三件事：**卡做好了在哪、怎么导入、下一步可以改什么**。
不要甩字段名和命令清单，用户不需要。

**「怎么导入」分两种**：电脑上给 `成品/<名>.card.json`（或直接给分发包）；
**手机上必须给 `成品/<名>.card.png`** —— 手机端只认带图的卡，`.json` 它读不进去，
而且它不会告诉你为什么，只会说「图片里没有 ElecKoi 角色卡数据」。预设同理：
`成品/<名>.preset.png` 走「预设管理器 → 导入预设」，分类**必须选「创作预设」**。

## 八、完整走一遍（照这个顺序抄）

用户说：**「给我做一张深夜便利店的卡，一个夜班店员，有点悬疑。」**

先问清楚三件事就够开工（不要自己编）：调子（都市 · 夜班 · 微悬疑）、
玩家是谁（新来的夜班店员）、有哪几个角色（店长 + 一两个常客）。

```
python forge.py new 深夜便利店
S=深夜便利店/source/深夜便利店.spec.yaml

# 骨架自带 5 条：开场白 / 世界总纲 / 规则·判定 / 名册·常用名字 / 可选·时局压力
python forge.py entry $S --列
python forge.py entry $S --删 "规则 · 判定"          # 这张卡用不上骰子
python forge.py entry $S --删 "可选 · 时局压力"

# 把「世界总纲」改成这张卡的世界（常驻：必须短、必须有插入位置）
python forge.py entry $S --改 "核心 · 世界总纲" --正文 "长夜便利店……"
# 「名册」改成常客清单，顺手把标题也改掉
python forge.py entry $S --改 "名册 · 常用名字" --标题 "名册 · 常客" \
        --正文 "……" --提示 "玩家问起某个常客的名字、或要跟谁搭话时读这条"

# 加角色（必读：每轮都在，但走 AI 读取）与世界观（关键词：说出专有名词才读）
# --分组 别省：不写就落「未分组」，做出来的设定库是一盘散的（名册 / 世界 是骨架自带的组）
python forge.py entry $S --新 "角色 · 阿岩" --模板 必读 --分组 名册 \
        --提示 "玩家和店员对话、或问起他时读这条" --正文 "……"
python forge.py entry $S --新 "世界 · 长夜便利店" --模板 关键词 --分组 世界 \
        --关键词 便利店,夜班,冷柜 --提示 "玩家问起这家店、夜班规矩时读这条" --正文 "……"

# 开场白：它不在 spec 里，用 opener 改（末尾那三个零宽标记由它负责，别手改 conf）
python forge.py opener 深夜便利店 --正文@开场白.txt

python forge.py check $S
python forge.py build $S 深夜便利店/成品/深夜便利店.card.json
python forge.py manual $S        # → 深夜便利店/文档/深夜便利店.手册.html
python forge.py index  $S        # → 深夜便利店/文档/深夜便利店.索引.md
```

做完那一刻应该长这样：`check` 报 **0 错**；`成品/深夜便利店.card.json` 是刚出的
（不是旧的）；`文档/` 下有手册与索引。交给用户时只说「卡做好了、在这里、怎么导入」。

**这一遍是从零建的。如果用户给的是一张现成的卡**，第 1 步换成（其余照旧）：

```
python forge.py analyze 他的卡.json                  # 先看是什么卡（只读）
python forge.py new 他的卡 --从 他的卡.json           # 要卡内界面：开一张带界面的新卡，内容用它的
# 只要内容、不要卡内界面：
python forge.py import 他的卡.json --到 .             # 收成内容层工程（各套开场方案都留着）
python forge.py check 他的卡                          # 看看接手的底子
```

（酒馆卡两条都认，会自动转 —— 转出来是草稿，末尾那三条提醒照着处理。）


## 九、红线 · 会被静默吃掉的写法

这些写法工具能查出来，但你一开始就不该写：

1. **读取策略写「变量条件」** —— 平台只认 `必读 / 选读 / 关键词` 三种，
   变量条件会被静默降级成选读。想靠推进阶段解锁内容，改用关键词。
2. **动态模式写 `single_condition`** —— 平台不认识它，会被当作标准模式。能用的是 `standard` / `ejs_reference`。
3. **用 `agent_read_condition` 表达「什么条件下读」** —— 平台根本不读这个字段，写了等于没写。
   「什么时候读我」这句话要写进**选择提示**。
4. **正文用 EJS 模板却没把内容模式切成 `ejs`** —— 模板会原样吐给玩家看。
5. **常驻条目没给插入位置/角色** —— 能跑，但约束力弱；核心准则要放在靠前位置、以 system 口气插入。
6. **关键词写内部才用的分类名** —— 玩家永远不会说出这个词，这条永远不触发。
7. **同一件事在两个地方各说一遍** —— 付两遍字数，还会互相打架。
   状态只有一个家：写进变量的，别再用文字复述。
8. **变量只写面板对象、没写初值与校验码** —— 运行时静默丢值（见「变量」那条的三处同步）。
