- **对应规程**：**§一第 3 步** 与 **§九红线第 5 条**；`entry` 裸跑用法里 `[--位置 …]` 无取值说明。

### #10 `domains` 缺「插入位置」的值域
- **想干什么**：查 `--位置` 的合法值，避免写错被拦。
- **卡在哪**：规程 §一说「值域字段写错会被当场拦……看全部合法值：`forge.py domains`」。但 `domains` 打印了 trigger/strategy/kind/dynamic/content/insert_role，**唯独没有 insert position（插入位置）的值域**。
- **怎么绕过去**：从样板条目「黑港城概览」抄 `instructions`。
- **对应规程**：**§一「值域字段写错会被当场拦下……看全部合法值：python forge.py domains」**——该命令给不出这个域。

### #11 `check <工程目录>` 与 `check <spec>` 输出详略不同
- **想干什么**：每改一轮体检、看常驻字数与策略分布。
- **卡在哪**：`check <工程目录>` 只报「批量校验 · N 个文件 · 0 个错误」，**不打**详表；`check <spec>` 才打常驻字数/触发方式/策略分布详表。规程「每改一轮就体检（也可以传整个工程目录）」没提这个差异。
- **怎么绕过去**：想看详表就改传 spec。
- **对应规程**：**§一第 5 步**。

### #13 `analyze` 对 ElecKoi 卡不列「开场白」
- **想干什么**：用 analyze 复核成品卡里的开场白。
- **卡在哪**：analyze 对**酒馆卡**会列出 `开场白 First Message …字`，对 **ElecKoi 卡**只列条目数/正则数/总字数，**没有开场白行**。
- **怎么绕过去**：改用 `entry --看 "AI角色开场白"` 或 `opener --看`。

### #14（附）开场白字数的两个数字

# 三、专节：`new --从` 这条路

### 参数怎么写
```
python forge.py new <新卡名> --从 <卡.json / 工程包.zip / spec.yaml / 工程目录> [--到 输出目录] [--id 前缀] [--模块 …]
```
- 我用的是：`new 盲跑测试卡 --从 "<样卡绝对路径>.json" --到 "<工作目录>/盲跑4"`。
- `--从` 直接跟路径即可，**没有额外坑**；中文卡名、中文路径、绝对路径都正常。
- 加 `--到` 可以指定工程落在哪（不加则落在当前目录，与规程 §一「工程落在 <当前目录>/我的卡/」一致）。

### 顺不顺手
- **顺手**。一条命令就把「界面层照抄骨架 + 内容层换成外来卡」做完了，不用人肉重建 10 条条目。规程 §二「`new --从` 就是『把条目搬过去』这条路」名副其实。
- 唯一的文档瑕疵是 #3（三处口径不一），但实操零影响。

### 每一步输出看不看得懂
- **看得懂**。输出把关键信息都给了：`灌进 10 条条目`、`开场白 取自外来卡 · 56 字`、`卡名 / id 前缀 / HUD 全局名`、`抄过来 N 个文件`。
- **一处会误导**：结尾打印 `卡名 盲跑测试卡`，但**这只是 conf 的卡名**，spec 里的 `character.name` 并没改。若我不看 check 的「卡片: 示例酒馆卡」，会以为卡名已经全对了（见 #2）。
- **有损提示到位**：多套开场被合并时，命令**当场**打了 `⚠` 警告并给出保多套的替代做法（`import` 收成内容档），规程 §二也预写了。这段体验很好。

# 四、专节：开场白改哪个文件

### 我改的文件
- 我用的是 `opener` 命令，**没有手动碰任何文件**：
  ```
  python forge.py opener <工程> --正文@开场白.txt
  ```
- 命令背后动的真源是 **`hud/hud.conf.json` 里的 `"开场白" → "正文"`**，再由它写回 spec 里 `fixed-opening-assistant` 那条。我从 `hud/hud.conf.json` 读到 `"开场白": {"条目": "fixed-opening-assistant", "正文": "...\u200b\u200b\u200b"}` 可以印证。

### 我怎么知道该改那儿
- **规程 §三直接讲了**，而且是**表格形式、一眼可辨**：
  - 有 `hud/hud.conf.json`（`new` 建的）→ 真源在 conf 的 `"开场白" → "正文"`，spec 里那条是**派生**；直接改 spec＝改了白改。
  - 只有 `source/`（`import` 进来的单张卡）→ **spec 里那条本身就是真源**，直接改就是对的。
- 另外 `opener <工程> --看` 会**主动打印真源位置**：`配置文件 ...\hud\hud.conf.json`，与规程说法完全一致。

### 规程说清「真源在哪」了吗
- **说清了，而且这是全规程写得最清楚的一节（§三）**。它同时覆盖了「有界面层 vs 只有 source」两种工程，还解释了末尾 3 个零宽标记（U+200B）的作用、`--补齐` / `--看` 的用途、以及 check 的两条兜底（`HUD-OPENER-MARK` / `HUD-OPENER-DRIFT`）。
- **本项无卡壳**。唯一提醒：这节的「表格 + 零宽标记」信息量最大，放在 §三比较靠前的位置很好，保持。

# 五、专节：静默点（怀疑会做错、但工具没拦）

1. **手改 spec 卡名（#2）—— 最典型的一处。**
   - 我怀疑：改 `character.name` 会不会算「改结构」、会不会被下次写回冲掉、会不会和 conf 卡名打架。
   - 工具反应：`check` 0 错 0 警告、`build` 正常、无任何提示。**做对了没奖励，做错了没惩罚**。
   - 佐证：#2 里「改名前 conf/spec 卡名已不一致、check 仍 0 错」就是铁证。

2. **酒馆「已禁用」条目被收进来（#8）。**
   - 我怀疑：`enabled:false` 的条目到底该不该进 ElecKoi。
   - 工具反应：照收，变 `keyword(禁)`，`check` 不报。**这是「看起来像真的、其实是假状态」的那类坑**（与规程 §五「变量」那条警告的口气同源）。

3. **常驻条目的插入位置（#9/#10）。**
   - 我怀疑：`--模板 常驻` 到底有没有默认位置、`--位置` 写什么值才合法。
   - 工具反应：成功回显不回显位置；`domains` 不给位置值域。只能事后 `--看` 反复确认。**没有当场拦、也没有当场确认**。

# 六、复核后的改口与澄清

按要求回头复核了此前结论，逐条交代：

- **无需改口的结论**：`--help`/`-h` 对子命令失效（已二次验证，`entry --help`、`entry -h` 均返回顶层帮助）；卡名两处不一致且 check 不报（已验证改名前就是这种状态）；「被禁的条目」仍以 `keyword(禁)` 存在于工程中（`entry --列` 可见）；`bundle` 会额外导出酒馆卡（输出原文可见）。**这些结论复核后成立。**

- **需要澄清的第二处**：`entry --列` 显示开场白 `261 字`、`opener` 显示 `258 字`，**不是冲突**，差的是末尾 3 个零宽标记（opener 统计口径「不含末尾标记」）。此前报告未点明，特此补上，避免读者误判。
