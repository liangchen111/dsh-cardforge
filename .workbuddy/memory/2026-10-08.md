## 第五轮（A+++ 落地）：模块可撤 + 版本号 + 皮肤系统

用户继续扣 1。做的是上一轮自己列的三件待办：`add` 的反操作、模块版本号、外观主题。

### 交付物
- **模块账本 `<工程>/模块账本.json`**（`forge/mods.py`）：每接一个模块记一笔 ——
  `id / 版本 / 接于 / 条目.替换[{id,title,原(整份),并入后(指纹)}] / 条目.新增[{id,title,指纹}] / 正则[ids] / 界面[文件]`。
  指纹 = `sha1(canonical json)[:12]`，用来判断「撤之前你动过没有」。
- **`forge drop <模块> <spec>`**（add 的反操作，按账本**精确**撤）：替换的还原、新增的删掉、
  正则按 id 删、`hud/模块/<名>/` 删目录 + 从 conf「模块」摘掉。**只撤账本里记着的**
  （手写进 spec 的东西一律不动）。接完又改过的会先警告再照撤。
  重复 `add` 自动跳过（不再覆盖账本 —— 否则「原样」会被自己的并入结果顶掉，撤不干净）。
- **模块版本号**：五个 `模块.json` 加 `"版本": "1.0.0"`；`forge mods --工程 X` 标 `●已接 / ○未接 / ▲仓库更新`。
  模块升级不自动覆盖卡（卡上的条目归卡），要吃新版得 `drop` 再 `add`。
- **皮肤系统 `forge/theme.py` + `assets/主题/`**：
  - `hud.css` 从「3 个色槽 + 一堆硬编码色」重写为 **19 个 `--hud-*` 槽**（文字 3 层 / 底色 4 层 /
    线 2 层 / 淡底 2 块 / 强调 + 警示 3 / 阴影 / 圆角 2 / 字体），**一个色值都不再硬编码**。
  - 五套皮肤：羊皮卷（默认）· 墨夜 · 霜白 · 朱砂 · 苔原。主题 JSON 只写想改的槽。
  - `forge theme <名> <工程>` 生成 `hud/主题.css`（只覆盖槽）；`--撤` 回核心默认；
    `--巡览 <工程>` 出「5 套皮肤 × 2 视图」对照图（`皮肤巡览.html`，~1.1MB，不落工程文件、不改现有皮肤）。
  - 组装顺序定为 **核心 → 皮肤 → 模块**（皮肤压核心换色，模块压皮肤保自己的强调色）。
  - 预览页外壳也跟着换色：主题可在「预览」里给 `底/字/强调`，其余（暗/线/框）由 `hud.py` 现推
    （`_rgba` / `_frame_color` 按亮度分深浅两路）。

   想知道「它现在写了什么」只能把整份 spec（几十条 × 三十来个字段）吞进去找一段话。
2. **长正文塞不进命令行** —— 正文动辄几百字、带换行，在 shell 里要跟转义规则搏斗，
   而 bash 的 `$'甲\n乙'` 到 cmd 就不认。跨平台没有一种通用写法。
两件事合起来才是「AI 能顺畅改一张卡」的闭环，所以本轮补它。

### 改了什么
- `forge/content.py` 新增 `entry_detail(spec, 谁)` —— 一条条目的全貌（正文全文原样、关键词、

- `forge.py` 的 `_opt()` 认 `@文件名`：值以 `@` 开头且是存在的文件 -> 从文件读内容，
  末尾一个换行按编辑器习惯忽略。**两种写法都认**（`--正文@正文.txt` 与 `--正文 @正文.txt`）。
  通用于所有文本参数（正文 / 标题 / 说明 / 正则模式与替换）。

## 第十二轮（用户扣 1）· 开场白：把这最后一处「手改文件」也收进命令

### 判断
上轮补完读写回路后，从零建一张卡的链路里**只剩一处还得手改文件**：开场白。
它是权重最高的字段（开卡第一屏），可真源在 `hud/hud.conf.json` 的 `"开场白"."正文"`，
spec 里那条只是派生物。更要命的是正文末尾**三个零宽空格（U+200B）** 是「建卡界面」
正则 `/\u200B{3}/` 的触发开关 —— 少一个，导入 ElecKoi 后建卡界面**静默消失**。
而 conf 里它写成一串 JSON 转义 `\u200b\u200b\u200b`：让 AI/人去手数、手写、手保，

### 改了什么

  顺带拦尖括号（会把标记变成可见字符，从会话预览露出来）与空正文。

  第一版直接 dump，结果是真字符写进文件：人打开 conf 再也看不见那三个标记（退化）。

## 第十八轮 · 变量改名 + 条目批量（版本 0.15.0 → 0.16.0）

真机实测已过（见上），这轮补两个一直挂着的可选缺口。两个都是**同一类**坑：
「这个名字不是一个孤立字符串，改一处另两处悄悄悬空」。

### 变量改名（新）
`var <spec> --改名 <变量 id 或 对象.变量> --成 <新名>` / `--改名对象 <对象> --成 <新名>`。
名字同时是**三处**：`variables[].title`、`initial_state` 里那一格的**键**、`schema_code` 里那个**字段名**。
以前只能删了重建 —— 那换的是 **id**（卡里按 id 引用的地方全断），而且另两处的键名也对不上。
- **id 不动**（只改 title）；顺序不动（`ZOD.rename_key` 原地保序，`emit` 按 kids 顺序出字，
  重排就等于把整段 schema 抖乱）。
- 对象改名：对象名 + `initial_state` 那一层 + Zod 那个嵌套对象键；子对象整棵跟着走
  （`variables[].object_id` 认 id，不受影响）。
- **正文里写着旧名字的地方只报不改** —— 工具分不清那是变量名还是恰好同字的常用词（叫「名」会命中一大片）。
- 同层重名当场拦下（两个同名，初值与 Zod 那两格会打架）。
- 回收站新增 `表="改名"`，撤销把三处**逐字**还原（自检里断言「改名前后整段 schema 只有名字变」）。

### 条目批量（新）
`entry --挪 / --删 / --启用 / --停用` 后面都能跟一串（`--挪 甲一 甲二 甲三 --到 世界`）。
- `content._认多条`：**有认不出的名字就整批停下、一条不动** ——
  「挪了 10 条其实进了 6 条」是最难收拾的状态。
- 一次落盘、**一条**回收记录（原来循环单条会写 N 条 trash，还原要按 N 次）。
- 批量删的位置按**从小到大**记（还原逐个插回原位），真删时**从后往前**删（否则前面一删后面全错位）。

## 第十五轮（续）｜变量换对象 `var --换对象 … --到 …`

用户扣 1 推进。上一轮遗留的那件（同一类坑：一个名字/一个挂靠，落在多处）。

### 做了什么
- **`forge/content.py` 新增 `move_variable(spec, 谁, 到)`**：名字不动，换它挂在哪个对象下。
  **四处一起搬**：`variables[].object_id` · `initial_state` 里那格（从旧对象树搬到新对象树）·
  `schema_code` 里那个字段（在 Zod 树上跟着搬）· `order` / `tree_view_order`（排到新对象末尾）。
  **变量 id 一个字母不动**（卡里按 id 引用的地方不会断）。
- **抽出一个通用原语 `_搬格子(st, 从, 到)`**：把状态树里某条路径的值搬到另一条路径（中途缺的层现建，
  目标写不进去就一个字节不动）。正向换对象与它的撤销**共用这一个**，免得正反两条路各写一份慢慢写岔。
- **`restore` 新增 `表="挪变量"` 撤销分支**：挂靠 / 初值 / Zod / 顺序 逐一还原（三处各自独立：
  当时哪处没跟着改，撤销也不凭空编）。
- **`forge.py cmd_var` 加 `--换对象 <变量> --到 <对象>`**；用法文本 + 顶层 HELP 同步。
- Zod 侧不加新原语：`node.kids[键].code` 取表达式 → `ZOD.drop` 摘 → `ZOD.set_leaf` 插，够用。

### 值得记的
- **新位置跟旧位置同一套写法**：有的卡是「对象名就是数据键」（`_找状态格子` 的候选乙，不去掉自己那层）。
  所以判据是「旧那格实际走的是标准写法还是去层写法」，新的跟着走 —— 同一张卡里风格必须一致。

## 第二十四轮：C 轨开工前的勘察 —— 挖出「可能不必写插件」

**本意**：查「插件里怎么拿到 forge.py 的执行权」。**结果**：查出一条更省的路。

**做法**：全程拆 `app.asar`（自己写的解析器）+ **只读**读用户数据（连 sqlite 都用 `file:…?mode=ro`）。

**发现一：ElecKoi 的 AI 手上本来就有命令行 + 文件工具。**
每个会话生成的那份预设 `dsh-runtime/generated-presets/eleckoi-active/preset.json` 里有 **16 个插件**，
含 `@deepseek-ai/dsh-tool-pwsh`（跑命令）、`@deepseek-ai/dsh-tool-fs`（读写文件）、
`dsh-tool-web`、`dsh-skill-filesystem` + `dsh-tool-skill`（技能系统）、卡内三件套、todo/jobs/goal/compaction。
会话日志开头三行固定是 `permission/preset = eleckoi-workspace`、`sandbox/mode = workspace-write`、
`approval/policy = never` —— **每个会话默认就是工作区权限**。
（`desktop-agent.patch.yml` 里那一大串 `disabled: true` 是**桌面基础层**的，会话层的预设又装上了。）

**发现二：AI 真的在调命令，但每次失败。**
会话 jsonl 里捞出的真实 `tool/call`：`Get-ChildItem -Force | Select-Object …`、
`Get-Random -Minimum 1 -Maximum 21`……结果全是 `(no output) [exit code: 3221225794]`。
同一会话里卡内工具（`eleckoi_*`）全部正常 ⇒ **只有「起子进程」这一件事坏**。

**发现三：坏在哪（推断）。**
`3221225794` = `0xC0000142` = `STATUS_DLL_INIT_FAILED`。排除两条：
① 不是「找不到命令程序」—— `dsh-pwsh-local` 的解析顺序末尾会**回退到系统自带的
`System32\WindowsPowerShell\v1.0\powershell.exe`**（本机有），本机只是没装 PowerShell 7；
② 不是「沙箱 runner 起不来」—— 官方写明 runner 跑前失败会打 `windows-acl-run:` 并**以 127 退出**，
我们拿到的是 `0xC0000142`，说明 **runner 起来了，是它拉起的 PowerShell 自己初始化失败**。
⇒ **推断：受限令牌沙箱下，系统自带的 5.1 起不来，pwsh 7 可以**（官方全篇按 pwsh 7 写，
5.1 只是降级路径）。**修法：装 PowerShell 7，重开 ElecKoi 再试。**

**发现四：还差一块拼图 —— 工作区在哪儿。**
沙箱是 `workspace-write`，工作区根是 `%APPDATA%\eleckoi-desktop\workspace`
（会话目录名 `--…-eleckoi-desktop-workspace--` 可见）⇒ **AI 写不到 `E:\workGZQ\制卡工具`**（读不受限）。
对得上号的官方功能：**创作工作室 Creator Studio** —— 一个「创作项目」= `rootPath` + `mode(blank|existing)`。
**推断**：把创作项目指到制卡工具/卡工程目录，会话工作区就挪过去，AI 就能在那儿跑 `forge.py`。
（此条**未验**。）

**产出**：`文档/ElecKoi内制卡·可行性勘察.md`（证据链 + 两步实测 + 出处表）；
README 路线图加了勘察指引；抽出来的证据副本在 `.workbuddy/_插件取证/`（前缀
`(工具集)`/`(会话运行时)`/`(命令行)`/`(作者SDK)`）。

## 第二十五轮：把上一轮的推断做成确证 —— 沙箱里跑不了 forge.py

> ⚠️ **先纠正第二十四轮**：那一轮的「本机没装 PowerShell 7、装一个就好」**是错的**，本轮实测证伪。
> 连带那条「`0xC0000142` 是当前版本的现象」也错：那 8 次失败全在 **9/25–9/27**，
> 而 `app.asar` 是 **10-07 14:02** 才更新的；10-08 的三个新会话**一次命令都没调过**。
> **「现在还能不能跑」原本根本没有数据。** 教训：查会话日志先看时间戳，再看 `app.asar` 的改动时间。

**做法**：写 asar 解析器把 ElecKoi 的沙箱代码**原样抽出**，在本机真跑 **11 组对照实验**
（`.workbuddy/_沙箱实测/`，含 `@deepseek-ai/dsh-sandbox-windows-acl`、`dsh-win32-process`、
`dsh-subprocess`、`koffi` 原生模块）。未改一行官方代码。

**实测表（决定性那几条）**：

| 层 | 结论 |
|---|---|
| 机制 | `init()` 建令牌 ✅；受限令牌下 `cmd` / **`powershell.exe`(自带 5.1)** / `node` 退出码**全 0**；全链路（宿主→`runner.js`→受限 pwsh）`windowsHide` 开/关、管道/继承**四种组合全通** |
| `forge.py` | 真身 python ✅（`Python 3.13.14`）；`PYTHONPATH` 生效 ✅（`yaml 6.0.3`）；`--help` ✅；能读工程 ✅；往工作区写 ✅；往 `E:\` 工程写 ❌（**设计如此**） |
| **边界** | **沙箱内 读✅ 写✅ 删❌ 改名❌ `os.replace`❌（全 `WinError 5`）；沙箱外全允许** |
| 对照 | 换位置（`%APPDATA%` vs `E:\workGZQ`）**一样**；换令牌高度（本进程**提权 High**）**一样** |

**为什么删不掉**：授权根同时加了能力 SID 的 `(OI)(CI)(W,D,DC)`、**`Everyone:(CI)(DENY)(DC)`**、
**Low 完整性标签**；且受限令牌里**禁掉了 `Authenticated Users`**（官方文档明写）——
而「用户删自己的文件」多半靠 `Authenticated Users:(M)`，它一禁，`DELETE` 就没了来源。

**为什么这条路就断在这儿**：`forge` 每次落盘都靠改名 ——
`content.commit()` 的 `os.replace`、`forge new` 的 `os.rename`、回收站的「移动进桶」。
⇒ **在 `workspace-write` 沙箱里跑 `forge.py` 必挂，`new` 第一步就过不去。**

**发现官方后门**：`pwsh` / `write` / `edit` 三工具共有 **`sandbox_permissions`**
（枚举 `workspace-write` / `danger-full-access` + 必填 `justification`）——
「沙箱刚拒掉的那条命令，用更宽模式重试一次，这次弹给用户批准」。
配一句官方红线：「被沙箱挡掉的文件操作是**策略拒绝：不要换法子重试**」⇒ **正路是升权，不是绕。**

**三条出路**（按代价）：① 把「做一张卡」压成一条命令 + 一次性升权（最快跑通）；
② 给 forge 加「沙箱友好模式」（不改名不删，丢原子性）；③ 走插件（宿主是独立 node 进程，
**不在沙箱里** —— 长期正解）。

**⚠️ 与官方文档矛盾**：`dsh-sandbox-windows-acl/README.zh.md` 写「基于 `DELETE` 的删除不受影响，
已被 runner 套件钉住」，我按它自己的代码复现却删不掉。**不下定论**，
写了一条**真机一分钟验证**（`Set-Content` → `Move-Item` → `Remove-Item` → `Write-Output "三条都过了"`），
按「看到什么 → 说明什么 → 下一步」给对照表。

**产出**：`文档/ElecKoi内制卡·可行性勘察.md`**整体重写**（错判纠正 / 可复现测法 / 三张结果表 /

**新记的坑（会再踩）**：
- **asar 的 `unpacked` 条目没有 `offset`**（只有 `unpacked: true`）。按 `offset or 0` 读会

## 第二十六轮：把上一轮的结论**做成能用的东西** —— forge 的「沙箱友好模式」（v0.22.0）

**为什么做这个**：上一轮证明了「ElecKoi 的沙箱里读✅写✅删❌改名❌」。而 forge 每次落盘都靠改名。
不做点什么，那条「让 AI 在 ElecKoi 里直接跑 forge.py」的路就是死的；
而路 ①（一次性升权）每次都要用户点批准，路 ③（插件）工作量大。
**路 ② 是唯一一条我现在就能替你走完的**，而且它不改变普通使用的任何东西。

**做法**：新增 `forge/sandbox.py`（一个开关 + 五个助手），把散在各处的删/改名调用点全部收口。

| 助手 | 干什么 |
|---|---|
| `land(临时, 目标)` | 普通＝`os.replace`；沙箱＝读出来**直接覆盖目标** |
| `rename(源, 目标)` | 同上语义，给 scaffold 换文件名用 |
| `remove` / `rmtree` | 删；删不掉返回 False，**永不抛** |
| `cleanup(临时)` | 收尾用，**与模式无关地永不抛**（以前 finally 里裸 `os.remove`，沙箱下会把成功报成失败） |
| `retire(记录)` | 让一份 JSON 作废：普通＝删，沙箱＝写墓碑 `{"_作废": true}` |
| `shell(路径, 原因)` | 让一份文件失效：普通＝删，沙箱＝写空壳（CSS/JS 注释、JSON 写 `{}`） |

**改动的调用点**：`content.commit`（核心落盘 + 临时文件挪去 `%TEMP%`）、`content._trim_trash`
/ `restore` / `clear_trash` / `list_trash`（墓碑）、`scaffold`（**文件名在抄的那一刻就换好**，
所以「改名 0 个」）、`mods._drop_hud`、`theme.clear_theme`、`pack.spec_to_card`、`dist`、`forge.py`。

**降级（明说的）**：
- 临时文件落进 `%TEMP%` —— 工程目录里留不下 `.forge-tmp-*`（不然 `check` 会当成第二份 spec）。
- 回收站「用掉一条」= 墓碑；`list_trash` 跳过 `_作废`，所以**用户看到的语义与删掉一样**。
- 撤皮肤 = 写一行 CSS 注释的空壳；`check` 认（试过了，0 错）。
- 撤模块 = **留目录**（组装只按 conf 的「模块」列表拼，留下的目录是死的）。
- `new --从` 接手失败 / `import` 收卡失败：**撤不掉刚建出来的目录**，但会**如实打一句**（不谎称干净）。

**门禁**：自检第 **42** 项 —— 把 `os.replace`/`os.remove`/`shutil.rmtree` 三个换成炸弹，
再跑「开新卡 → 加条目 → 出成品 → 验卡」，**全程一次都不许碰到那三个**。一次就绿。
`cmd_selftest` 开头会把沙箱模式**临时关掉**（有几项靠删文件摆场景，沙箱下会假报错）。

## 第二十九轮 · 一次落成：卡稿落卡（v0.25.0）

上一轮给 AI 装上「工具」，再上一轮给了「知识」。这一轮解决**轮次** ——
AI 在对话里做一张卡要跑 5~10 次工具调用，每次都是一整轮（上下文从头重发一遍）。
用户对成本敏感，**轮次才是大头**。

### 做了什么：`forge.py make <卡稿.yaml>`

照一份「这张卡该长什么样」的 YAML，一趟走完
建工程 / 写条目 / 加变量正则 / 换开场白 / 出成品 / 体检。新模块 `forge/draft.py`。

四条设计：

1. **条目按标题认人**（upsert）—— 已有同名的改它、没有才新建。AI 于是不必先摸清骨架里
   现成有什么，也不必背命令的先后。
2. **全程在临时目录里做（`tempfile.mkdtemp`），全绿了才整棵拷到目标位置。**
   这是这个命令的灵魂：稿子有毛病时**目标位置一个字都不会被写**。
   拷贝用自写的 `_拷树`（只创建、只覆盖）而不用 `copytree` —— 后者要求目标不存在，
   而「目录在了但是空的」是常见处境，为迁就它先 rmdir 会在沙箱里撞墙。
3. **预检一次报全**：静态能查的（模板名 / 类型 / 值域会不会被静默降级）在动手之前全报，
   不让 AI 改一处跑一次。值域那块**调 `domain.check_entry_domains`**，不另写一份表
   （两份表迟早漂移，而那正是护城河）。
4. **只输出一份报告** —— 底下 add_* / set_* / HUD / opener 全静音
   （opener 那一路的 out 本来就能透传，传个 `_静` 进去就行）。
   一次落成的价值一半是只跑一次、另一半是**只读到一句结论**。

配套：`make --模板` 出一份能直接跑的骨架；`--试` 只验证不出；`--覆盖` 才让重落
（**只认同一张卡**：目标里有 `source/<卡名>.spec.yaml` 才算，别人的东西一律不碰）。

### 踩到的坑

- **「清空条目」的语义**：第一版写成「先清后建」，于是稿子里「改已有条目」那几条会先被清掉、
  再当新条目建回来 —— 报告成了「改 0 · 新建 4 · 删 4」，看着像丢了一条；万一半路失败还会真丢内容。
  改成**先建后清**（清掉「稿子里没提到」的那些）。
- **预检里的模板名**：认不出时没 `continue`，后面还去 `CONTENT.模板表[模板]` → KeyError。
  而 `main` 把 KeyError 当「代码自己的 bug」打栈 —— 这次正好被它照出来。
- **规程里的命令写法会被自检解析**：规程写 `--模板 > 我的卡.yaml`，第 29 项把 `>` 当成了模板名。
  → **加新命令时要想着「第 29 项会怎么读这句话」。**

## 第三十轮 · 示例卡稿 + 「改已有条目」那两条静默路（v0.26.0）

### 起因：`--示例` 是句谎话

`cmd_make` 里 `--模板` / `--示例` / `--sample` 三个都走 `卡稿模板()` ——
**说了有示例、给的却是同一份空壳骨架**。「照它抄」这件事，抄到的还是空格占位。

### 修的（全是「不报错但结果不对」那一类）

1. **给已有条目写 `模板:` 会当场抛 `ContentError`**（不是 DraftError）：
   `模板表` 里带着 `kind`（身份字段），而 `set_entry` 明确不收身份 → 一串 traceback。
   修：拿**同一份** `CONTENT.可改字段` 过滤一遍再递过去。
   （为什么以前没暴露：`_模板`, 自检第 44 项都只在**新条目**上写 `模板:`。）
2. **给已有条目写 `分组:` 被默默忽略**：`分组` 不在 `set_entry` 的可改字段里，
   代码把 `等等` 里的 `分组` 直接跳过了 —— 稿子写着「分组: 角色」，条目纹丝不动、**一个字都不报**。
   修：真去 `CONTENT.move_entries()`，并把结果记进报告的 `挪组` 一行。
   判据用新增的 `_组名(spec, gid)`（分组 id -> 名字）比，同组就不挪。
3. **变量跟骨架里现成的重名 → traceback**：`add_variable` 在 `落卡` 里**不在 try 里**，
   它抛的 `ContentError` 穿出 `cmd_make`（那边只接 `DraftError`）。修：catch 住换成一句人话。
